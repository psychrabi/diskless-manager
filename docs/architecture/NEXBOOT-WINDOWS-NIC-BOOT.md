# NexBoot and shared Windows NIC boot

**Scope:** source-level comparison of NexBoot's default branch with this repository's Windows diskless boot path, checked 2026-11-07. NexBoot links below point to its first-party source and documentation; the local implementation references describe the current working tree where noted.

## What NexBoot does

NexBoot shares an image/restore point, then gives each client a writable ZFS clone. Its documented NIC fallback derives that PC's boot configuration from an installed donor NIC and a matching driver. The implementation makes this a per-terminal identity operation: `BootService.buildBootScript` calls `Identity.Prepare` before `CreateClientLUN`; `Service.prepareTemplate` chooses direct boot, a reusable/generated template, capture through WinPE, or a blocked result; `Service.buildLayer` asks the host agent to create the client's identity layer using its MAC, PnP instance, and template. [README](https://github.com/waterlemon0108/nexboot/blob/main/README.md), [boot.go: `buildBootScript`](https://github.com/waterlemon0108/nexboot/blob/main/internal/control/boot.go), [identity/service.go: `prepare`, `prepareTemplate`, `buildLayer`](https://github.com/waterlemon0108/nexboot/blob/main/internal/control/identity/service.go), [identity/template.go: `planTemplate`, `modelInstance`](https://github.com/waterlemon0108/nexboot/blob/main/internal/control/identity/template.go)

The generated configuration is substantially more than a driver file or `Start=0`. `winreg.ApplyGenerated` resolves a matching INF already registered in the image's DriverStore, checks the actual boot binary, and rejects NetAdapterCx NICs for this iSCSI path. It exports an installed donor's network-class key, `Enum` instance, service, TCP/IP/TCPIP6 linkage and interface keys, GUID, and MAC-related state; `materialize` rewrites them for the target instance, GUID, MAC, service, and INF. If those inputs cannot be safely derived, the template path can defer to capture or fail instead of inventing a device binding. [generate.go: `ApplyGenerated`, `resolveDriver`](https://github.com/waterlemon0108/nexboot/blob/main/internal/winreg/generate.go), [generate.go: `exportDonor`, `identifyDonor`, `materialize`, `driverKeys`](https://github.com/waterlemon0108/nexboot/blob/main/internal/winreg/generate.go)

Keep the identifiers distinct. A PnP **instance ID** identifies one enumerated device and is used for the target's `Enum` registry path. A **hardware ID** or **compatible ID** matches the model to an INF/package and is appropriate for a hardware-wide early-boot mapping. NexBoot's generator accepts the target instance, derives PCI hardware/compatible IDs for driver resolution, and rewrites the exact target instance. Its iPXE hardware hints identify a PCI vendor/device and bus location, not a Windows instance path. [generate.go: `GenerateSpec`, `ApplyGenerated`, `pciIDs`](https://github.com/waterlemon0108/nexboot/blob/main/internal/winreg/generate.go), [hwprofile/hints.go: `ParseBusID`, `ProfileFromHints`](https://github.com/waterlemon0108/nexboot/blob/main/internal/control/hwprofile/hints.go)

When the existing image cannot be safely adapted from an installed donor, NexBoot has a client-bound WinPE path. Its WinPE documentation requires a recovery/ADK environment compatible with the Windows image and describes loading the target driver's package. The documented validation is limited: it records a Windows 11 22621 UEFI VMware adaptation and says BIOS validation is outstanding. [WinPE README](https://github.com/waterlemon0108/nexboot/blob/main/tools/winpe/README.md)

## Comparison with this repository

At local `HEAD`, WinPE reported every physical adapter's `PNPDeviceID` and selected the first IP-enabled MAC before locating the iSCSI session. A PnP instance ID identifies one enumerated device; its hardware-ID prefix can still match an INF, but it is not the adapter's complete `HardwareID`/`CompatibleID` inventory. The old flow could include unrelated NICs, miss alternate compatible IDs, or pair the IDs with a different adapter's MAC. The adaptation manifest selected drivers but returned `WindowsBootArmConfig::default()`, so it did not bind the reported boot NIC to a boot-start service. See the prior versions of [`install.ps1`](../../src-tauri/src/infrastructure/pxe/installer/install.ps1) and [`installation_service.rs`](../../src-tauri/src/application/installation_service.rs) at `HEAD`; local `pnp_id_matches` shows the prefix tolerance in driver selection ([`driver_selection.rs`](../../src-tauri/src/infrastructure/pxe/driver_selection.rs)).

The current **uncommitted working tree** addresses those gaps: `install.ps1` reads connections from the assigned iSCSI session, follows its initiator IP to one physical PnP adapter, and sends its hardware/compatible IDs and MAC. `adaptation_manifest` verifies that MAC against the client assigned to that WinPE session and uses the package IDs and NIC groups recorded when the assignment was prepared; it checks that the actual WinPE adapter is covered before returning the full boot-arm config. The shared assignment path loads known preboot and verified client inventories, selects the union of matching packages, and creates one expected-ID group and early-boot mapping for each known adapter. [`install.ps1`](../../src-tauri/src/infrastructure/pxe/installer/install.ps1), [`installation_service.rs`: `adaptation_manifest`](../../src-tauri/src/application/installation_service.rs), [`windows_servicing.rs`: inventory and `prepare_assignment`](../../src-tauri/src/api/handlers/windows_servicing.rs), [`windows_boot_arming.rs`: `boot_arm_config_for_nics`, CDDB planning](../../src-tauri/src/infrastructure/pxe/windows_boot_arming.rs)

This local design targets a **shared serviced revision**: all inventoried NIC packages and CriticalDeviceDatabase (`ControlSet…\Control\CriticalDeviceDatabase`) bindings are written into the candidate image, with a hard coverage check for each NIC group. Existing CDDB entries count only when their Service points to a registered kernel NIC driver and their ClassGUID is the network class. WinPE publication now creates a persistent `serviced-<revision>` snapshot and completes the revision record; a later client with the same source, NIC set, driver packages and arm policy reuses it. NexBoot instead builds each client's Windows adapter identity in its own identity layer before exposing the normal boot LUN. CDDB can arrange for a mapped NIC service to start before disk-based PnP; it does not itself create NexBoot's per-instance `Enum`, network-class, GUID, MAC, and TCP/IP records. The local architecture note makes this boundary explicit and requires real SAN-boot acceptance for new hardware. [`windows_boot_arming.rs`: `WindowsBootArmConfig`, `plan`, `critical_device_boot_nics`](../../src-tauri/src/infrastructure/pxe/windows_boot_arming.rs), [Windows driver boot-arming design](WINDOWS-DRIVER-BOOT-ARMING.md)

## Practical conclusion and limits

For one common Windows image, the minimum viable boot contract is: inventory the adapter that actually carries the firmware/iSCSI session; match its hardware/compatible IDs to a complete compatible driver package; make that driver's service available early enough for the iSCSI root; and apply the same contract to every known NIC family in the shared revision. The current working-tree approach implements that contract with per-adapter CDDB mappings and a coverage gate. A NexBoot-style per-client identity layer is the stronger option if a target also needs its own exact `Enum`/network identity before normal PnP; the source comparison does not establish that CDDB alone will work on every Windows build or NIC.

Source review cannot demonstrate a successful hardware SAN boot. NexBoot's own WinPE notes report one UEFI VMware case and leave BIOS unverified. This repository also documents real SAN boot as the acceptance gate. A newly inventoried NIC expands the shared revision scope; clients on an older revision need reassignment to receive that expanded driver/binding set.
